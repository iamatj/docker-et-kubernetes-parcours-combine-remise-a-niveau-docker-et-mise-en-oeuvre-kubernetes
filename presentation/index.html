Le concept

Conteneur ou machine virtuelle

Machine virtuelle

Un système complet avec son propre noyau, sur un hyperviseur. Démarre en minutes, pèse des Go. Isolement fort.

Conteneur

Un processus de l'hôte, isolé par les namespaces et limité par les cgroups. Partage le noyau. Démarre en millisecondes, pèse des Mo.

Complémentaires

En production, les conteneurs tournent… dans des VM : celles du cloud, ou les nœuds de votre cluster.

Question : pour isoler deux clients qui ne se font pas confiance, que choisir ? (la VM, ou un conteneur dans une VM).

Le concept

Client, daemon, API

  • docker (le client) envoie des requêtes HTTP
  • dockerd (le daemon) construit, télécharge, lance
  • par le socket /var/run/docker.sock
  • containerd et runc lancent vraiment les conteneurs
  • Docker Engine (Linux) ou Docker Desktop (une VM sur Windows et macOS)

# le client n'est qu'un client HTTP
curl --unix-socket /var/run/docker.sock \
  http://localhost/version

# Compose V2 : sans tiret
docker compose version
docker-compose   # V1, retiré en juin 2023

Le groupe docker donne l'équivalent de root sur la machine : à dire clairement. Vocabulaire : image, conteneur, registry, daemon, Dockerfile, Compose.

Le concept

Une image : des couches et une configuration

  • chaque instruction qui ajoute des fichiers = une couche en lecture seule
  • les couches sont partagées et mises en cache
  • le conteneur ajoute une couche en écriture, jetable
  • nom complet : registre/dépôt:tag, ou @sha256:…
ÉcritSignifie
nginxdocker.io/library/nginx:latest
mirror.gcr.io/library/postgres:17-alpinemiroir public de Docker Hub

Le concept

docker run et le cycle de vie

docker run -d --name vitrine \
  -p 8081:8080 \
  -e POSTGRES_PASSWORD=… \
  --memory 256m --cpus 0.5 \
  --restart unless-stopped \
  ghcr.io/nginx/nginx-unprivileged:1.28-alpine

  • create → start → stop → rm, et restart
  • logs, exec, inspect, stats au quotidien
  • -it pour un shell, --rm pour un conteneur jetable
  • la mémoire est une limite dure (OOM), le CPU un plafond
Montrer docker inspect : tout ce qu'on cherchait dans l'incident (image, options, redémarrages) y est.

Le concept

Les instructions du Dockerfile

InstructionRôlePiège
FROMimage de départ, une par étapelatest, image complète inutile
RUNexécute une commande, crée une coucheun apt-get update seul en cache
COPY / ADDcopie des fichiersADD décompresse et télécharge
ENV / ARGvariable du conteneur / du buildun secret dans un ARG reste visible
EXPOSEdocumente un portne publie rien
ENTRYPOINT / CMDprogramme / arguments par défautforme texte : pas de signal d'arrêt
Insister sur ENTRYPOINT + CMD en forme JSON : PID 1 reçoit SIGTERM, le conteneur s'arrête proprement.

Le concept

Multi-stage et BuildKit

FROM python:3.13-slim AS construction
RUN python -m venv /opt/venv
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt

FROM python:3.13-slim
RUN useradd --uid 10001 cordee
COPY --from=construction /opt/venv /opt/venv
COPY app.py .
USER 10001
ENTRYPOINT ["gunicorn"]

  • slim, alpine (musl), distroless (sans shell)
  • .dockerignore : .env, caches, .git
  • BuildKit : builder par défaut depuis Docker Engine 23
  • étapes en parallèle, cache fin, RUN --mount pour cache et secrets
Faire remarquer que l'étape construction n'est jamais livrée : ni pip ni cache dans l'image finale.

Le concept

L'architecture d'un cluster

Control plane

API Server : la seule porte d'entrée · etcd : l'état du cluster · Scheduler : choisit un nœud · Controller Manager : fait converger le réel vers le voulu

Nœuds de travail

kubelet : lance les pods de son nœud · container runtime (containerd) · kube-proxy : les Services · le CNI (Calico) : le réseau des pods

On y accède par

kubectl (CLI) · une interface web (Headlamp, le Dashboard historique a été retiré) · l'API REST directement

Dessiner au tableau le trajet d'un kubectl apply : API Server → etcd → contrôleur → scheduler → kubelet → containerd.

Le concept

Les objets fondamentaux

ObjetRôleGéré par

Le concept

Un Deployment en YAML

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: cordee
spec:
  replicas: 3
  selector:
    matchLabels: {app: api}
  template:
    metadata:
      labels: {app: api}
    spec:
      containers:
        - name: api
          image: ghcr.io/iamatj/cordee-api:1.0

  • indentation par espaces, jamais de tabulation
  • yes, 3 ne sont pas des chaînes : "yes"
  • le selector doit correspondre aux étiquettes, et il est immuable
  • kubectl apply --dry-run=server valide sans créer
Faire remarquer les deux étiquettes app: api surlignées : c'est le lien Deployment → pods.

Chapitre 7 · l'incident

Samedi · 8h02

La 1.1 a coupé le site

« Et à 8h20, quelqu'un a livré une 1.2 qui n'existe pas. »
— Sophie
  • Pendant une minute, une partie des clients voit « API injoignable ».
  • Personne ne sait quelle version tournait juste avant.
Demander comment on revient en arrière sans savoir quelle version tournait : l'historique des ReplicaSets.

Le concept

Rolling update et rollback

spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1         # un pod de plus
      maxUnavailable: 0   # jamais un de moins
  minReadySeconds: 5

kubectl rollout status deployment/api
kubectl rollout history deployment/api
kubectl rollout undo deployment/api

  • un nouveau ReplicaSet monte, l'ancien descend
  • kubernetes.io/change-cause pour un historique lisible
  • une image introuvable bloque la mise à jour, sans couper
  • le fichier reste la référence : set image est un geste d'urgence
Prévenir : même avec maxUnavailable 0, quelques erreurs restent au TP 07. La réponse arrive au TP 08 : les sondes.

Chapitre 8 · l'incident

Mercredi · 14h

Le mot de passe sur GitHub

« Et quand la base tombe, le site envoie encore les gens vers des API en erreur. »
— Sophie
  • Le dépôt a été public trois heures, mot de passe en clair dedans.
  • Kubernetes ne voit rien : les conteneurs tournent.
Deux problèmes : la configuration mêlée au code, et l'absence de sondes. Le TP 08 traite les deux, puis la méthode de diagnostic.

Le concept

Étiquettes, ConfigMap, Secret

  • étiquettes : pour sélectionner (-l tier=back)
  • annotations : pour décrire (responsable, change-cause)
  • ConfigMap : la configuration hors de l'image
  • Secret : les données sensibles… en base64, pas chiffrées

envFrom:
  - configMapRef: {name: cordee-config}
  - secretRef:    {name: cordee-db}

# lire un Secret, c'est facile :
kubectl get secret cordee-db \
  -o jsonpath='{.data.DB_PASSWORD}' | base64 -d

Les limites des Secrets

etcd non chiffré par défaut, lisibles avec un droit get, et dans Git en clair base64 : Sealed Secrets, External Secrets, SOPS.

Une variable d'environnement est lue au démarrage : changer la ConfigMap ne change rien sans rollout restart.

Le concept

Démarré, prêt, vivant

SondeQuestionSi elle échoue
startupProbeas-tu fini de démarrer ?redémarrage au bout du délai
readinessProbepeux-tu recevoir du trafic ? (/readyz)retiré du Service, pas redémarré
livenessProbees-tu encore vivant ? (/healthz)redémarré

Diagnostic : get → describe (Events) → logs --previous → get events → get endpoints. En ouverture : DaemonSets, affinité et anti-affinité.

Piège : la base dans la liveness. Si elle tombe, toutes les API redémarrent en boucle sans rien réparer.

Chapitre 9 · l'incident

Jeudi · 6h50

47 réservations perdues

« J'ai passé la matinée au téléphone avec des familles en colère. »
— Léa
  • worker-2 a redémarré pour une mise à jour de sécurité.
  • Le pod PostgreSQL a été recréé, avec un emptyDir neuf.
Rappeler que c'était annoncé dès le TP 06 (question 6).

Le concept

PV, PVC, StorageClass

  • un PVC : « je veux 1 Gi en ReadWriteOnce »
  • une StorageClass crée le PV à la demande
  • reclaimPolicy : Delete efface tout avec le PVC, Retain garde
  • WaitForFirstConsumer : créé là où le pod est placé

Stateless

le site, l'API : on les multiplie, on les tue, on les déplace.

Stateful : StatefulSet

la base : un nom stable (postgres-0), son propre volume (volumeClaimTemplates), un Service headless, un ordre de démarrage.

Sur le lab, local-path stocke sur le disque du nœud : simple, mais le volume ne suit pas le pod sur un autre nœud. Sur un cloud, ce serait un disque réseau.

Le concept

RBAC : qui peut faire quoi

ObjetPortée
Roleun namespace
ClusterRoletout le cluster, et les nœuds, PV…
RoleBindingdonne un rôle dans un namespace
ClusterRoleBindingdonne un rôle partout

  --as=system:serviceaccount:equipe:karim

ServiceAccounts : l'identité des pods. Par défaut, chaque pod reçoit un jeton : automountServiceAccountToken: false quand il n'en a pas besoin.

Le concept

Network Policies et SecurityContext

# plus rien n'entre…
podSelector: {}
policyTypes: [Ingress]
---
# …sauf l'API depuis le site
podSelector: {matchLabels: {tier: back}}
ingress:
- from: [{podSelector: {matchLabels: {tier: front}}}]
  ports: [{port: 8000}]

Seulement avec un CNI compatible (Calico, Cilium) ; le trafic du nœud (sondes) reste permis.

securityContext:
  runAsNonRoot: true
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities: {drop: [ALL]}
  seccompProfile: {type: RuntimeDefault}

Pod Security Admission

étiquettes du namespace : enforce: baseline, warn: restricted.

Prévenir : appliquer le refus par défaut avant les autorisations casse le site. C'est voulu dans le TP, pour le voir.

Le concept

Helm : un modèle, des valeurs

helm/cordee/
  Chart.yaml

  • chart : le paquet · release : une installation · repository : d'où il vient

  • Traefik et Headlamp du lab sont déjà des releases
