Ce que fait Huiteo

Livrer l'application avec son environnement

Une image

Docker

Le concept

Monolithe ou microservices

Monolithe

un seul programme fait tout, livré d'un bloc

  • simple à installer et à comprendre
  • une correction = tout relivrer, tout redémarrer
  • on agrandit tout, même la partie qui ne sert pas
  • une panne peut tout emporter

Microservices

plusieurs petits services, chacun son rôle

  • chacun livré, mis à jour, agrandi séparément
  • une image et un conteneur par service
  • plus de pièces : réseau, supervision, versions
  • les conteneurs rendent ce découpage praticable

Huiteo RDV

déjà découpée en trois : le site (nginx), l'API (Python), la base (PostgreSQL). Trois images, trois conteneurs : Karim peut livrer l'API sans toucher au site.

Le concept

Conteneur ou machine virtuelle

Machine virtuelle

Un système complet avec son propre noyau, sur un hyperviseur. Démarre en minutes, pèse des Go. Isolement fort.

Conteneur

Un processus de l'hôte, isolé par les namespaces et limité par les cgroups. Partage le noyau. Démarre en millisecondes, pèse des Mo.

Complémentaires

En production, les conteneurs tournent… dans des VM : celles du cloud, ou les nœuds de votre cluster.

Le concept

Client, daemon, API

  • docker (le client) envoie des requêtes HTTP
  • dockerd (le daemon) construit, télécharge, lance
  • par le socket /var/run/docker.sock
  • containerd et runc lancent vraiment les conteneurs
  • Docker Engine (Linux) ou Docker Desktop (une VM sur Windows et macOS)

# le client n'est qu'un client HTTP
curl --unix-socket /var/run/docker.sock \
  http://localhost/version

# Compose V2 : sans tiret
docker compose version
docker-compose   # V1, retiré en juin 2023

Le concept

Le socket, la porte du daemon

# un fichier spécial : s = socket
ls -l /var/run/docker.sock
srw-rw---- 1 root docker 0 … docker.sock

# systemd garde la porte
systemctl status docker
TriggeredBy: ● docker.socket

# parler au daemon sans le client
curl -s --unix-socket /var/run/docker.sock \
  http://localhost/version | jq

Un socket Unix

une prise entre deux programmes, sous forme de fichier : pas d'adresse IP, pas de port, seulement dans la machine. Comme un fichier, il a des droits : root et le groupe Linux docker en lecture et écriture, personne d'autre.

Qui passe par cette porte ?

la commande docker, docker compose, VS Code, la CI, Portainer, la supervision : tous envoient des requêtes HTTP et reçoivent du JSON. L'API est la vraie interface de Docker.

Activation par socket

systemd écoute le socket et réveille dockerd au premier appel. Pour l'arrêter vraiment : systemctl stop docker docker.socket.

Le concept

Du docker run au processus

docker

le client : votre commande

▼ requête HTTP sur /var/run/docker.sock

dockerd

le daemon : API, images, réseaux, volumes

▼ gRPC

containerd

le cycle de vie des conteneurs

▼ un shim par conteneur, puis runc

votre processus

isolé par les namespaces, limité par les cgroups

# deux services systemd
systemctl is-active docker containerd
# le conteneur est un processus du poste
docker run -d --name dodo busybox sleep 600
ps -ef --forest | grep -B1 "sleep 600"
docker inspect -f '{{.State.Pid}}' dodo
# sans daemon, plus de client
sudo systemctl stop docker docker.socket
docker ps # Cannot connect…

À retenir pour l'exploitation

arrêter ou mettre à jour dockerd arrête les conteneurs, sauf "live-restore": true dans /etc/docker/daemon.json. Journaux : journalctl -u docker.

Le concept

Docker Compose : à quoi ça sert ?

Sans Compose : une commande par pièce, dans le bon ordre

docker network create huiteo
docker volume create donnees-db
docker run -d --name db --network huiteo \
  -v donnees-db:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=… postgres:17-alpine
docker run -d --name api --network huiteo … huiteo-api:1.0
docker run -d --name front -p 8080:8080 … huiteo-front:1.0

Avec Compose : tout est décrit dans un fichier

# compose.yaml
services:
  db:    { image: postgres:17-alpine, volumes: … }
  api:   { build: ./api, depends_on: [db] }
  front: { build: ./front, ports: ["8080:8080"] }

  • l'application entière dans un fichier YAML, versionné avec le code
  • docker compose up -d : crée réseaux, volumes et conteneurs, dans l'ordre
  • docker compose down : arrête et supprime (les volumes restent)
  • un plugin du client : il parle au daemon par le même socket
  • docker compose (V2, avec un espace) ; docker-compose (V1) est abandonné depuis 2023
  • une seule machine : pour plusieurs serveurs, Kubernetes (jour 2)

Quand ?

pour un poste de développement, un environnement de test, une petite application sur un serveur. En détail au chapitre 4, TP 03.

Le concept

Le groupe docker, c'est root

ls -l /var/run/docker.sock
srw-rw---- root docker …

cat /etc/shadow # Permission denied
docker run --rm -v /etc:/hote busybox \
  head -3 /hote/shadow # ça passe

  • le daemon tourne en root
  • écrire sur le socket = commander le daemon
  • donc lancer un conteneur root qui monte /, ou --privileged

Qui met-on dans le groupe ?

ceux à qui on donnerait sudo. Un audit du groupe docker est un audit des administrateurs.

Limiter le risque

sudo docker (journalisé) ; Docker rootless ou Podman ; jamais le socket exposé en TCP sans TLS ; monter le socket dans un conteneur en connaissance de cause (Trivy au TP 04).

docker run --rm

supprime le conteneur dès qu'il se termine. Pour les commandes ponctuelles (un test, un outil, une lecture) : pas de conteneurs Exited qui s'accumulent dans docker ps -a. Sans --rm, hello-world est resté, d'où le docker rm.

À quoi a servi hello-world ?

vérifier toute la chaîne en une commande : le client parle au daemon par le socket, le daemon télécharge l'image (étape sautée : le script l'avait déjà), crée le conteneur, qui affiche son texte et se termine en Exited (0), c'est-à-dire sans erreur.

Un conteneur vit tant que sa commande tourne

sleep 600 : 10 minutes. Sans commande, BusyBox lance sh, qui s'arrête aussitôt. Après un docker run -d, vérifiez toujours avec docker ps.

Le concept

Multi-stage et BuildKit

FROM python:3.13-slim AS construction
RUN python -m venv /opt/venv
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt

COPY --from=construction /opt/venv /opt/venv
COPY app.py .
USER 10001

1 · ClusterIP le défaut

Joignable depuis le cluster seulement : un nom DNS (api) et une IP virtuelle stable. kube-proxy choisit un pod, sur n'importe quel nœud. Chez Huiteo : l'API, la base.

2 · NodePort

N'importe quel nœud, port 30000 – 32767, même un nœud sans le pod. Chez Huiteo : le site sur :30080 (TP 06).

3 · LoadBalancer

Une adresse externe : MetalLB dans ce lab, le cloud ailleurs. Elle arrive sur un nœud, puis suit le chemin du NodePort. Le site sur 10.10.0.201 (TP 07).

4 · port-forward pas un Service

Un tunnel de votre poste vers un pod, à travers l'API Server, le temps d'une session. Pour déboguer, jamais pour les clients.

Gigognes : un LoadBalancer crée un NodePort, qui crée un ClusterIP.

Stratégie

Rolling update : un nouveau, puis un ancien en moins

Dans Kubernetes

spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # un pod de plus
      maxUnavailable: 0  # jamais un de moins
  minReadySeconds: 5
kubectl rollout status  deployment/api
kubectl rollout history deployment/api
kubectl rollout undo    deployment/api
  • chaque version est un ReplicaSet : le nouveau monte, l'ancien descend
  • kubernetes.io/change-cause pour un historique lisible
  • une image introuvable bloque la mise à jour, sans couper
  • le fichier reste la référence : set image est un geste d'urgence

Stratégie

Recreate : tout arrêter, puis tout relancer

Dans Kubernetes

spec:
  strategy:
    type: Recreate

Quand

  • deux versions ne peuvent pas coexister (schéma de base, format de fichier)
  • un volume qu'un seul pod peut monter : PostgreSQL (TP 07, question 8)

Pour · contre

Simple, aucune ressource en plus. Une coupure à chaque livraison, et autant au retour arrière.

Stratégie

Blue/green : deux environnements, une bascule

Dans Kubernetes

Deux Deployments, api-blue et api-green, et un Service qui choisit :

kubectl patch service api -p \
 '{"spec":{"selector":
   {"app":"api","version":"green"}}}'

Pour · contre

  • bascule et retour instantanés, version testée avant le trafic
  • deux fois les ressources pendant la bascule
  • la base est partagée : elle doit convenir aux deux versions

Stratégie

Canary : un pod de la nouvelle version parmi les anciens

Dans Kubernetes

Deux Deployments avec le même label app=api, derrière le même Service. On déplace les replicas :

kubectl scale deploy/api-v1-0 --replicas=3
kubectl scale deploy/api-v1-1 --replicas=1

Pour 5 % plutôt que 25 % sans 20 pods : des poids dans la Gateway API (TP 11), weight: 95 / weight: 5.

Rolling update ou canary ?

Le rolling update ajoute un pod neuf puis en retire un ancien, et va jusqu'au bout tout seul. Le canary remplace un pod existant et s'arrête : vous décidez de la suite.

Stratégie

A/B testing : deux versions, deux groupes

Dans Kubernetes

Gateway API : une règle par en-tête.

rules:
- matches:
  - headers:
    - name: X-Groupe
      value: b
  backendRefs: [{name: api-v1-1, port: 8000}]
- backendRefs: [{name: api-v1-0, port: 8000}]

Canary ou A/B ?

Canary : une part au hasard, pour vérifier que ça marche. A/B : un groupe choisi, pour savoir ce qui marche le mieux, souvent pendant des jours.

Stratégie

Shadow : la nouvelle version écoute en silence

Dans Kubernetes

Gateway API : un filtre de copie.

filters:
- type: RequestMirror
  requestMirror:
    backendRef:
      name: api-v1-1
      port: 8000

Pour · contre

  • aucun client exposé, vraie charge
  • deux fois le calcul
  • effets de bord : écritures, mails, paiements à neutraliser

Le concept

Trois façons de donner la configuration à un pod

Le concept

Les sondes : la journée d'un conteneur

RESTARTS 0

La chambrestartupProbe

🛏️
Chez Huiteo, pendant le réveildemarrer() attend PostgreSQL, crée les tables, remplit les études. Tant que Flask n'écoute pas, GET /healthz : connexion refusée. Ailleurs : une JVM qui chauffe, des migrations.
startupProbe: httpGet: {path: /healthz, port: 8000} periodSeconds: 2 failureThreshold: 30 # 60 s pour se lever

La portereadinessProbe

🚪
Chez Huiteo, « prêt ? »GET /readyz lance SELECT 1 sur PostgreSQL. Base injoignable : 503, plus de clients, sans redémarrage : redémarrer ne réparerait pas la base.
readinessProbe: httpGet: {path: /readyz, port: 8000} periodSeconds: 5 failureThreshold: 2 # pas de clients

Le bureaulivenessProbe

🖥️
Chez Huiteo, « tu travailles ? »GET /healthz répond {"statut": "ok"} sans toucher à la base : sinon, une panne de PostgreSQL redémarrerait tous les pods.
livenessProbe: httpGet: {path: /healthz, port: 8000} periodSeconds: 5 failureThreshold: 3 # puis redémarrage
🧑‍🔧kubelet
