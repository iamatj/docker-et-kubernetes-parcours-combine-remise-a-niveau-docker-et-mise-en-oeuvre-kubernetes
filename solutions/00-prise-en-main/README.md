# Correction du TP 00 – Prise en main du poste et de Docker

**1.** Les numéros dépendent de l'installation (Docker Engine 28 ou 29 au moment de la formation). L'important : il y a deux programmes, le client et le serveur, qui peuvent avoir des versions différentes ; ils s'entendent sur une version d'API (`API version`, par exemple 1.5x). Un client plus récent sait parler à un daemon plus ancien en baissant sa version d'API.

**2.** Dans `/var/lib/docker` (`DockerRootDir`) : couches des images, systèmes de fichiers des conteneurs, volumes. Le pilote de stockage est `overlayfs` (ou `overlay2`). Le socket `/var/run/docker.sock` est ouvert par `dockerd`, lancé par systemd ; il appartient à `root:docker`.

**3.** Sans daemon, le client ne sait presque rien faire : `docker ps` échoue avec `Cannot connect to the Docker daemon`. Seules les commandes locales répondent (`docker version` affiche le bloc `Client`, puis l'erreur). Le conteneur `dodo` n'a **pas** survécu : à l'arrêt, `dockerd` arrête ses conteneurs, et au redémarrage il ne relance que ceux qui ont une politique `--restart` (`dodo` n'en avait pas : il est `Exited`). Conséquence en production : mettre à jour ou redémarrer Docker coupe les applications, sauf si on a activé `"live-restore": true` dans `/etc/docker/daemon.json` (les conteneurs continuent de tourner pendant que le daemon redémarre). La chaîne complète : `docker` (client) → `dockerd` (API, images, réseaux, volumes) → `containerd` (cycle de vie des conteneurs) → `containerd-shim-runc-v2` (garde un œil sur un conteneur) → `runc` (crée le processus avec ses namespaces et ses cgroups, puis s'efface). Le même `containerd` sert de runtime à Kubernetes au jour 2, sans `dockerd`.

**4.** Tout ce que fait le client passe par cette API REST : une chaîne CI, un IDE, un outil de supervision, Compose lui-même pilotent Docker sans le client. `docker compose up` n'est qu'une suite d'appels à cette API (créer un réseau, un volume, des conteneurs).

**5.** Qui peut écrire sur le socket commande le daemon, et le daemon tourne en `root`. Il lance donc pour vous un conteneur `root` qui monte n'importe quel dossier du poste : `/etc/shadow`, mais aussi `/` tout entier (`-v /:/hote`), ou qui démarre en `--privileged`. Être dans le groupe `docker` revient à être `root` sur la machine. On ne le donne qu'à ceux à qui on donnerait `sudo`. Pour limiter le risque : réserver Docker aux administrateurs (`sudo docker …`, journalisé) ; utiliser **Docker en mode rootless** (le daemon tourne sous le compte de l'utilisateur) ou Podman ; ne jamais exposer le socket sur le réseau (`-H tcp://…` sans TLS) ; ne monter le socket dans un conteneur qu'en connaissance de cause (on le fera pour Trivy au TP 04). Sur un serveur, un audit qui liste les membres du groupe `docker` liste en fait des administrateurs.

**6.** Le client contacte le daemon ; le daemon télécharge l'image depuis le registre ; il crée un conteneur et lance son programme ; il renvoie la sortie au client, qui l'affiche. Le téléchargement n'a pas eu lieu : l'image était déjà présente (préchargée par `lab/preparer-jour-1.sh`). Sans elle, on aurait vu `Unable to find image … locally` puis `Pulling from …`.

**7.** Compose V1 (le programme Python `docker-compose`) n'est plus maintenu et a été retiré des distributions Docker depuis juin 2023. Compose V2 est un plugin du client écrit en Go : `docker compose`. On remplace `docker-compose` par `docker compose` dans les scripts ; le fichier `docker-compose.yml` reste lu, mais le nom recommandé est `compose.yaml`, et la clé `version:` en tête de fichier est obsolète (ignorée). « V2 » désigne une génération, pas un numéro : `docker compose version` affiche aujourd'hui une version 2.x ou plus récente.

**8.** Un **Dockerfile** décrit comment construire une **image** ; une image (des couches en lecture seule et une configuration) est stockée dans un **registry** ; le **daemon** télécharge l'image et en crée des **conteneurs** (des processus isolés qui ajoutent une couche en écriture) ; **Compose** décrit dans un fichier YAML un ensemble de conteneurs, réseaux et volumes qui forment une application.

**9.** La machine virtuelle embarque son propre noyau ; les conteneurs partagent celui de l'hôte (isolement par namespaces et cgroups). Pour deux études clientes qui ne se font pas confiance, l'isolement d'une VM (ou d'un conteneur dans une VM, comme sur les offres managées) est plus sûr : une faille du noyau touche tous les conteneurs d'un même hôte. Conteneurs et VM sont complémentaires : Huiteo fera tourner des conteneurs… dans des VM.

**Bonus.** Contextes : Docker Desktop fait tourner le daemon dans une petite VM Linux (WSL 2 sous Windows, une VM dédiée sous macOS), le client restant sur le poste. Différences : Desktop est une application graphique avec une licence payante au-delà d'une certaine taille d'entreprise ; le réseau et les montages de fichiers traversent la VM (plus lents, `host` ne se comporte pas pareil) ; Desktop peut embarquer un Kubernetes local. Docker Engine sur Linux est gratuit, sans VM, et c'est ce qu'on trouve sur les serveurs et les agents de CI. Dans `busybox`, le conteneur ne voit que ses propres processus (`ps` montre `sh` en PID 1), il a son propre nom d'hôte (l'identifiant du conteneur) et sa propre interface réseau (`eth0` en 172.17.x.x sur le pont `docker0`). `docker system df` montre quelques Go d'images : surtout `python:3.13` (environ 1 Go).
